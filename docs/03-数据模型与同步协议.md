# 数据模型与同步协议

## 核心表（MySQL）

- profiles：id、display_name、timezone、created_at、updated_at。
- users：id、email、password_hash、email_verified_at、status、created_at、updated_at。
- email_verifications：id、user_id、email、code_hash、expires_at、attempts、used_at、created_at。
- task_lists：id、owner_id、name、color、sort_order、archived_at、deleted_at、created_at、updated_at、version。
- tasks：id、list_id、creator_id、parent_task_id、title、note、status、priority、due_at、sort_key、tags、completed_at、deleted_at、created_at、updated_at、version、field_clocks。
- task_attachments：id、task_id、file_name、mime_type、size_bytes、storage_key、created_at、deleted_at；文件保存在服务端 storage 目录，客户端文件保存在 App 专属存储目录。
- sync_operations：operation_id、user_id、entity_type、entity_id、operation_type、payload、client_timestamp、created_at、applied_at；operation_id 唯一。
- sync_changes：递增 change_id、实体类型、实体 ID、操作类型、变更载荷和服务端时间。

field_clocks 使用 JSONB 保存字段级逻辑时间，例如 {"title":12,"status":15}，用于合并不同字段的并发修改。

## 同步协议

客户端保存 last_change_id。同步分两步：

1. pull(after_change_id)：拉取服务端变更，事务写入本地库，成功后推进游标。
2. push(operations[])：批量提交本地操作，服务端按 operation_id 幂等执行，返回 accepted、conflict 或 rejected。

建议接口为 POST /api/v1/sync/push 和 GET /api/v1/sync/pull?after=...。客户端每 10~30 秒拉取一次，回到前台、网络恢复和用户手动刷新时立即拉取。

## 冲突策略

- 不同实体分别应用。
- 同一实体不同字段按字段合并。
- 同一字段并发修改比较服务端逻辑时钟；相同则按服务端接收顺序，并记录冲突日志。
- 删除与编辑冲突时删除优先；回收站恢复生成新的恢复操作。
- 版本不匹配返回当前实体和冲突字段，客户端合并后重试。

本地待同步记录状态为 pending、sending、synced、conflict、failed。UI 展示已同步、同步中、离线、同步失败，并允许重试。
